# Дані: імпорт із таблиці, резервні копії

- Для кого: власник/розробник. Код `prisma/import-real.ts`, `prisma/import-delta.ts`, `prisma/local-guard.ts`, `scripts/export-journal.py`, `data/` (gitignored).

## Призначення

Безпечно переносити дані з Google-таблиці викладача в базу і не втратити нічого з уже налаштованого (розклад, пари, студенти, внесені оцінки).

## Що робить зараз

- `export-journal.py`: xlsx → `data/journal.json`.
- `import-real.ts --wipe`: одноразовий знищувальний імпорт (відмовляється працювати не на localhost без `ALLOW_REMOTE_DB=1`).
- `import-delta.ts`: **лише додає** відмітки, оцінки, колонки, результати модуля, по батькові; нічого не перезаписує, не воскрешає видалене; без `--apply` лише звіт; з `--apply` спершу `data/backup-*.json`; повторний запуск додає 0.

## Правила й інваріанти

- Спершу перевірка на `ge_import`, потім dry-run на Neon, порівняння, лише тоді `--apply` **[підтверджено]**.
- Знищувальні дії (`--wipe`, `db:reset`, `TRUNCATE`, видалення на Neon) — лише з окремим дозволом у діалозі.
- `pg_dump` v16 несумісний із Neon (PG 18): резервні копії — експорт через Prisma (JSON).
- Дати в таблиці бувають із помилкою в місяці (22.10 замість 22.09): не створювати за ними нових занять.
- Спірне виносити у звіт для користувача, не вирішувати мовчки.

## Напрямок

Поступовий перехід від таблиці до застосунку як єдиного джерела істини; імпорт XLSX прямо в застосунку (беклог).

## Покращення (за пріоритетом)

1. Пошук семестру/студентів у `import-delta` з урахуванням року й статусу; не відмічати заняття `CANCELLED/MOVED`; повторювані ПІБ у групі не зливати мовчки.
2. Захист `db:reset` від віддаленої бази.
3. Автоматичний регулярний бекап Neon (JSON) і перевірка відновлення (ROADMAP фаза 2).
4. Рішення користувача щодо спірних місць таблиці: АТТт-22 21.09, КІт-31 ПП 12.10, дві зміни модуля, дати поза розкладом, нетипові назви колонок, колонка «ц».

## Відкриті питання

- Спірні місця таблиці (вище); планові години, тематичні плани, по батькові, статуси — чекаємо даних.
