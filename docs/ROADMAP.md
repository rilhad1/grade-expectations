# Дорожня карта: 4 фази, 2 перевірки

Фази випливають із концепту: у MVP — кеш PWA без черги змін, повна офлайн-синхронізація у фазі 2, ролі завідувача/студента й AI у фазі 3. Номери етапів посилаються на `PLAN.md`.

## Фаза 1. MVP (етапи 0–5, ≈65 д)

**Мета:** провести один семестр в одному коледжі онлайн: деканат створює семестр і публікує розклад, викладачі відмічають пари й ведуть журнал, атестації й відомості формуються автоматично.

| Віха          | Етапи | Результат                                                                     |
| ------------- | ----- | ----------------------------------------------------------------------------- |
| 1.1 Фундамент | 0–1   | Монорепо, схема БД, seed, повний `@ge/domain` з тестами                       |
| 1.2 Доступ    | 2     | Вхід, ролі TEACHER/MODERATOR, ізоляція за коледжем                            |
| 1.3 Деканат   | 3     | Семестри, групи, навантаження, конструктор, публікація, запити на перенесення |
| 1.4 Викладач  | 4     | «Сьогодні», «На парі», журнал, тематичний план                                |
| 1.5 Документи | 5     | Атестації, відомості PDF/DOCX, ICS, експорт даних                             |

Не входить: офлайн-черга, AI, студентський кабінет, мультиколедж-адміністрування.

### Перевірка 1 (кінець віх 1.3–1.4)

Деканат і 2–3 викладачі проходять реальний сценарій на справжніх даних (групи ПДт-11/12/13, поточний розклад). Критерії: відмітка групи з 25 студентів ≤15 с; розклад деканату відтворюється без обхідних шляхів; список знайдених розбіжностей з практикою закладу. Результат: правки бізнес-логіки (OQ-1…6) до початку віхи 1.5.

## Фаза 2. Офлайн і надійність (етап 6, ≈10 д + стабілізація 5 д)

**Мета:** режим «На парі» працює без інтернету.

- Dexie, `outbox`, `/sync/push`, `/sync/pull`, `ChangeLog`.
- Конфлікти: останній запис по клітинці для оцінок і відвідуваності, `version` для структури.
- PWA: кеш оболонки, індикатор синхронізації, push-нагадування.
- Бекапи `pg_dump` у S3-сховище, перевірка відновлення, Sentry, uptime.
- Постановка Postgres RLS (як другий рубіж ізоляції), 2FA для модераторів.

### Перевірка 2 (кінець фази 2)

Польові випробування: тиждень пар з вимкненим Wi-Fi, часткові обриви, два пристрої одного викладача. Критерії: жодної втраченої відмітки; всі конфлікти або вирішені автоматично, або показані користувачеві. Результат: рішення про запуск у другому коледжі.

## Фаза 3. Ролі та розумні функції (≈20 д)

- `COMMISSION_HEAD`: навантаження й вичитка викладачів комісії, зведені атестації.
- `ADMIN` закладу: користувачі, шаблони відомостей, довідники.
- `STUDENT`: власні оцінки й пропуски за посиланням або в кабінеті.
- AI (Claude API): імпорт розкладу з фото у чернетку, генерація тестів за темою, чернетка робочої програми.
- Банк завдань і генерація варіантів контрольних із друком у PDF.
- Аналітика: зона ризику, звіти по групах.

## Фаза 4. Масштабування (за потребою)

- Кілька коледжів: самореєстрація організацій, налаштування шкал і формул на рівні закладу, шаблони відомостей по закладах.
- Інтеграції: імпорт/експорт з державних систем обліку (за наявності API), синхронізація Google Calendar у два боки.
- Тарифи й оплата, підтримка, моніторинг навантаження, шардування або окремі БД, якщо знадобиться.

## Залежності між фазами

```text
Фаза 1 ──► Перевірка 1 ──► Фаза 2 ──► Перевірка 2 ──► Фаза 3 ──► Фаза 4
 (MVP)       (правки          (офлайн)   (запуск у         (ролі, AI)  (масштаб)
             логіки)                     2-му коледжі?)
```

Фаза 3 може частково йти паралельно з фазою 2 (AI й студентський кабінет не залежать від синхронізації), але лише після Перевірки 1.
