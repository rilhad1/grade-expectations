# Журнал рішень (ADR)

## ADR-001. Монорепо pnpm + Turborepo, TypeScript strict

- **Контекст.** Спільні типи й Zod-схеми між фронтом, бекендом і доменом.
- **Рішення.** pnpm workspaces, Turborepo, ESM усюди, строгі прапорці TS.
- **Наслідки.** Один `packageManager`; на машині розробника pnpm зараз не запускається через corepack — виправляється на етапі 0.

## ADR-002. `@ge/domain` — чисті функції без I/O

- **Контекст.** Ті самі правила потрібні на сервері й офлайн у браузері.
- **Рішення.** Пакет без залежностей від Prisma, fetch і Node API; 100% покриття гілок.
- **Наслідки.** Дати передаються рядками `YYYY-MM-DD`, а не `Date`, щоб уникнути проблем із часовими поясами.

## ADR-003. Ідентифікатори UUID v7 від клієнта і Better Auth

- **Контекст.** Офлайн-створення потребує id на клієнті; Better Auth за замовчуванням керує власною таблицею користувачів та генерує id.
- **Рішення (пропозиція).** Для доменних сутностей — UUID v7 з клієнта. Таблицю `User` узгодити з Better Auth через його `advanced.database.generateId`; перевірити на етапі 2 до написання коду.
- **Наслідки.** Якщо узгодження неможливе, лишаємо окремий `User` з посиланням на таблицю Better Auth.

## ADR-004. Поле `Lesson.manuallyEdited` (пропозиція, чекає підтвердження — OQ-7)

- **Контекст.** Регенерація не має чіпати вручну змінені заняття, але схема цього не відображає.
- **Рішення.** Додати булеве поле, що виставляється при ручній зміні дати, пари, аудиторії чи статусу.
- **Наслідки.** Невелика зміна схеми до першої міграції, тому нічого переписувати не доведеться.

## ADR-005. Інтеграційні тести проти справжнього Postgres

- **Контекст.** Docker на машині відсутній.
- **Рішення.** Тестова БД через Docker Compose (за промптом). Якщо Docker не буде встановлено, альтернатива — локальний Postgres 16 з тим самим `DATABASE_URL`.
- **Наслідки.** Домен-тести не залежать від БД і працюватимуть у будь-якому разі.

## Прийняті рішення (за делегуванням власника продукту)

Власник доручив приймати рішення самостійно; бізнес-логіку він скоригує окремо. Усе нижче вважається прийнятим і замінює «пропозиції» вище.

- ADR-003: UUID v7 від клієнта, `User` узгоджується з Better Auth на етапі 2.
- ADR-004: додати `Lesson.manuallyEdited` (OQ-7).
- OQ-8: окремий `TeachingLoad` на кожен вид занять, UI групує.
- OQ-9/OQ-2: `Grade.value` для PASS_FAIL — 1/0; заліки зберігаються у `AttestationResult.final` як рядок.
- OQ-10: 2FA відкладено до фази 2.
- OQ-11: лишаємо I семестр у seed; терміни переглядаємо після Перевірки 1.
- Docker: потрібен для етапу 0; якщо не встановлено, використовується локальний Postgres 16 (ADR-005).

## ADR-006. Версії залежностей (етап 0)

- TypeScript закріплено на 6.0.3: typescript-eslint 8.71 підтримує `<6.1`, а TypeScript 7 ще ні.
- MUI закріплено на 7.3.11 згідно з концептом (на сьогодні є v9); оновлення — окремим ADR.
- Версії у `package.json` — точні (без `^`), pnpm 12.9.1 через `packageManager`.
- Залежності зі скриптами збірки заборонені за замовчуванням (`allowBuilds`); дозволяти лише за потреби.

## ADR-007. Перейменування полів, що конфліктують зі службовим `version`

- **Контекст.** Службове поле `version` (лічильник для синхронізації) є в кожній моделі, а в концепті `Schedule.version` і `DisciplineProgram.version` означали інше.
- **Рішення.** `Schedule.revision` (номер версії розкладу) і `DisciplineProgram.edition` (редакція програми). `Lesson.scheduleVersion` зберігає `Schedule.revision`.
- **Наслідки.** DTO й домен використовують `revision`/`scheduleVersion`.

## ADR-008. Ізоляція за коледжем: розширення Prisma зараз, Postgres RLS — у фазі 2

- **Контекст.** Дані належать коледжу, але лише частина таблиць має `organizationId` напряму (Room, Student, Discipline тощо). Решта (Lesson, Grade, Enrollment) прив'язана через зв'язки.
- **Рішення.** `forOrganization(prisma, orgId)` (`apps/api/src/plugins/tenant.ts`) примусово додає `organizationId` до всіх запитів моделей із цим полем і перезаписує значення від викликача. Дочірні моделі ізолюються через зв'язки в `repo.ts` і перевірку `can()`. RLS відкладено до фази 2: для дочірніх таблиць політики потребують або денормалізованого `organizationId`, або join-політик, а це краще проєктувати разом із синхронізацією.
- **Наслідки.** Новий `repo.ts` для дочірньої моделі зобов'язаний фільтрувати через зв'язок із коледжем; для цього є тести ізоляції (`tenant.test.ts`).

## ADR-009. Better Auth: користувачі лише за запрошенням, роль-перемикач на клієнті

- **Контекст.** Деканат створює облікові записи викладачів; одна людина може мати кілька ролей.
- **Рішення.** Самореєстрація вимкнена (`disableSignUp`, також для Google). `User` відповідає моделі Better Auth через `user.fields.name = fullName`; id генерує `uuidv7()` (ADR-003). Сервер перевіряє права за **об'єднанням** ролей; перемикач ролі в меню — лише налаштування інтерфейсу (бейдж, навігація), на права не впливає. База даних сесій — Postgres, cookie httpOnly.
- **Наслідки.** Інвайти й скидання пароля — етап 3 (потрібна пошта). 2FA — фаза 2 (OQ-10).

## ADR-010. Схеми оновлення без значень за замовчуванням

- **Контекст.** У Zod 4 `.partial()` зберігає `.default()` усередині полів: PATCH без поля скидав його до значення за замовчуванням (слот втрачав аудиторію, семестр — періоди).
- **Рішення.** Значення за замовчуванням задаються лише в схемах створення; схеми оновлення будуються з базових полів без них. Регресійний тест `dto/updates.test.ts` перевіряє, що кожна схема `update*`, розібрана лише з `version`, не містить інших ключів.
- **Наслідки.** Нова схема оновлення має бути додана в цей тест.

## ADR-011. Публікація розкладу: незмінні версії та точний підрахунок годин

- **Контекст.** Опублікований розклад породжує заняття, на які посилаються оцінки та відвідуваність.
- **Рішення.** Опублікована версія розкладу незмінна; зміни йдуть у нову чернетку (копія останньої опублікованої), одна чернетка на семестр. Публікація блокується конфліктами, рахує різницю «створено / скасовано / без змін» і генерує заняття лише від «сьогодні» (`ctx.today()`); проведені, відмічені й змінені вручну заняття не чіпає. Перевищення годин рахується із згенерованих занять, а не з приблизної кількості тижнів.
- **Наслідки.** «Сьогодні» береться з `app.clock.today()` (Europe/Kyiv); у тестах підміняється.

## ADR-012. Обмеження спроб входу: IP + пошта, без вбудованого ліміту Better Auth

- **Контекст.** Вбудований ліміт Better Auth для `sign-in/email` (3 спроби / 10 с з одного IP) блокував би цілу аудиторію викладачів за спільним NAT коледжу, а ліміт на весь `/auth/*` ламав `get-session`, який клієнт викликає при кожній навігації.
- **Рішення.** Ліміт Fastify лише на входи, реєстрацію й відновлення пароля: 10 спроб на хвилину за ключем «IP + пошта». Вбудований ліміт Better Auth для входу, `get-session` і виходу вимкнено.
- **Наслідки.** Перебір пароля одного облікового запису обмежений, інші користувачі з того самого IP не страждають. Додатковий захист від розподіленого перебору — фаза 2 (2FA, блокування облікового запису).

## ADR-013. e2e на Playwright з окремою БД

- **Контекст.** Критичні сценарії деканату треба перевіряти в справжньому браузері, не чіпаючи dev-дані.
- **Рішення.** `pnpm e2e` піднімає API (:3101) і web (:5273) на базі `ge_e2e`, яку скрипт `e2e/global-setup.ts` створює з нуля (лише для імен `*_e2e`), накочує міграції (`migrate deploy`) і сидом. `prisma migrate reset` не використовується: Prisma блокує його, коли команду запускає агент, і вимагає явної згоди користувача.
- **Наслідки.** Сценарії послідовні й залежать від сид-даних; у CI e2e йде після збірки.

## ADR-014. TanStack Table 8, а не 9

- **Контекст.** На момент етапу 4 `@tanstack/react-table` має гілку 9.x з іншим API (`useTable`, features); концепт не фіксує версію.
- **Рішення.** Журнал на `@tanstack/react-table` 8.21.3 + `@tanstack/react-virtual`: перевірений API (`useReactTable`, `getCoreRowModel`). Перехід на 9 — окремим ADR, коли він стабілізується.
- **Наслідки.** Таблиця використовується лише для моделі колонок і рядків; розмітка — власна сітка CSS із закріпленими колонками й віртуалізацією рядків.

## ADR-015. Підміна «сьогодні» лише для e2e

- **Контекст.** Сценарії на кшталт «сьогодні пара о 10:00» залежать від системної дати.
- **Рішення.** Змінна середовища `FAKE_TODAY` (YYYY-MM-DD) підміняє `ctx.today()` на сервері; у production її наявність — помилка конфігурації. Браузер у e2e отримує той самий момент через `page.clock.setFixedTime`.
- **Наслідки.** Серверні тести використовують `app.clock.today = …`; e2e — `FAKE_TODAY=2026-10-12`.

## ADR-016. Аудит оцінок і відвідуваності в ChangeLog

- **Рішення.** Кожна зміна оцінки, відмітки відвідуваності й статусу заняття пишеться в `ChangeLog` (хто, коли, пристрій з `X-Device-Id`, значення до/після) у тій самій транзакції. Оцінка видаляється м'яко.
- **Наслідки.** Історія змін оцінки доступна в БД; екран історії — пізніше. `ChangeLog` же стане основою синхронізації на етапі 6.

## ADR-017. Фонові задачі через pg-boss, документи в БД

- **Контекст.** Відомості (особливо PDF через Gotenberg) і експорт усіх даних можуть тривати секунди; HTTP-запит не має їх чекати. Окремий брокер (Redis) для MVP зайвий.
- **Рішення.** Черга на pg-boss у тій самій Postgres (схема `pgboss`). `POST /documents` створює запис `GeneratedDocument` (PENDING) і ставить задачу в чергу; воркер формує файл і зберігає його в `GeneratedDocument.content` (bytea), клієнт опитує `GET /documents/:id`. Драйвер задач перемикається `JOBS_DRIVER` (`pgboss` | `inline`): у тестах inline виконує задачу в процесі одразу, окремий тест перевіряє реальний pg-boss. PDF — через Gotenberg (`GOTENBERG_URL`); без нього лишається DOCX, а `/me` повідомляє `features.pdf = false`.
- **Наслідки.** Файли в БД простіші за S3 на старті (відомості — десятки кілобайт), але потребують очищення старих записів і винесення у S3 у фазі 2 разом із бекапами. Версію pg-boss зафіксовано на 12.35.1: свіжіша 12.37.0 порушувала `minimumReleaseAge` pnpm, а виняток із цієї перевірки ми не додаємо.

## ADR-018. ICS-підписка за секретним токеном, «плаваючий» час

- **Контекст.** Google/Apple Calendar підписуються на URL без cookie й без заголовків авторизації.
- **Рішення.** `GET /api/v1/calendar/<token>.ics` публічний, доступ — за випадковим 192-бітним токеном (`CalendarFeed`), який викладач може замінити (старе посилання одразу дає 404). Події — без `TZID` (локальний «плаваючий» час) з `X-WR-TIMEZONE:Europe/Kyiv`; вікно — від 14 днів тому до 240 днів уперед, скасовані пари з `STATUS:CANCELLED`, перенесені оригінали не експортуються.
- **Наслідки.** Токен у URL — те саме, що «посилання з доступом»: його не можна логувати публічно. Для користувачів в іншому часовому поясі час покажеться локальним; VTIMEZONE додамо, коли з'явиться такий сценарій.

## ADR-019. Офлайн «На парі»: outbox поверх локальної копії, LWW по клітинці

- **Контекст.** Пара йде в аудиторії, де Wi-Fi нестабільний; відмітка групи з 25 студентів не має залежати від мережі. Концепт вимагає чергу змін, `/sync/push` і `/sync/pull`.
- **Рішення.**
  - Dexie (`ge-offline`) тримає заняття викладача у вікні ±2 тижні від сьогодні (готові `LessonDetailDto` з ростером, відмітками й оцінками), чергу `outbox`, службові значення (курсор, кеш `me`, дзвінки, семестри) і сповіщення про результат синхронізації.
  - Усі дії на парі — операції (`attendance.set`, `grade.set`, `grade.delete`, `lesson.info`, `lesson.finish`, `lesson.reopen`). Операція однією транзакцією Dexie застосовується до локальної копії й потрапляє в чергу; UI не чекає на сервер, а онлайн іде тим самим шляхом, тож він завжди протестований.
  - `POST /sync/push` застосовує пачку по черзі й ідемпотентний за `opId` (`SyncOp`). Бізнес-відмови (заняття скасовано, немає прав, оцінка поза шкалою) повертаються як `rejected`, програш у конфлікті — як `skipped/SUPERSEDED`; клієнт показує їх користувачу.
  - `GET /sync/pull?since=` повертає змінені заняття (за `updatedAt` самого заняття, відміток чи оцінок) з курсором із запасом 2 с; без `since` — повний знімок. Не відправлені локальні зміни накладаються поверх відповіді сервера.
  - Конфлікти відвідуваності й оцінок — «останній запис перемагає» по клітинці за часом дії на пристрої (`editedAt`), а не за часом приходу на сервер; час із майбутнього обрізається до серверного «зараз». REST-запис теж ставить `editedAt`.
- **Чому не `ChangeLog` як джерело дельти.** `ChangeLog` — аудит (до/після), а не повний стан; дельта за `updatedAt` охоплює і онлайн-правки з десктопа, і зміни, що не пишуться в аудит. `ChangeLog` лишається журналом.
- **Наслідки.** Журнал-таблиця, розклад, атестації, довідники й експорти — лише онлайн (як і в концепті). Журнал-сітка після відновлення зв'язку бачить зміни одразу, бо вони вже на сервері.

## ADR-020. PWA: оболонка в кеші Workbox, дані — тільки через Dexie

- **Рішення.** `vite-plugin-pwa` (generateSW) кешує всю оболонку (включно з ледачими чанками) і віддає `index.html` для навігації, крім `/api/*`. Відповіді API Service Worker не кешує: офлайн-читання йде через Dexie (`cachedFetch` для `/me`, довідників, семестрів; `loadLesson`/`loadToday` для занять).
- **Наслідки.** Застосунок можна встановити на телефон (іконки 192/512 і maskable). TanStack Query працює в `networkMode: 'always'`, інакше він ставить мутації на паузу, поки браузер офлайн.

## ADR-021. Вихід з акаунта й зміна користувача очищують локальну базу

- **Рішення.** При виході спершу відправляється черга; якщо зміни лишилися, користувач підтверджує втрату. Після підтвердження база очищується. При вході іншого користувача (`meta.userId`) база теж скидається.
- **Наслідки.** На спільному пристрої дані попереднього викладача не лишаються; незбережені зміни не губляться мовчки.

## ADR-022. Редизайн UI: токени → тема MUI, спільні компоненти, перестилізація замість переписування

- **Контекст.** Макети Claude Design (`design/`) описують цілісну візуальну мову, а логіка, хуки й офлайн-шар уже протестовані.
- **Рішення.** Токени з `design/tokens.json` живуть у `app/theme/tokens.ts` і подаються в тему MUI 7 з CSS-змінними (`colorSchemes` світла/темна, перемикач «Світла / Темна / Як у системі», скрипт у `index.html` без миготіння). Спільні елементи (`StatusChip`, `GradeChip`, `LessonCard`, `SegmentedControl`, бейджі, `StatCard`, `EmptyState`, скелетони, діалоги) лежать у `shared/ui`; екрани перестилізовано, а їхня поведінка, `data-testid` і доступні імена збережено. Шрифт — Golos Text, self-hosted (`@fontsource/golos-text`, кирилиця й латиниця), бо `@fontsource/golos-ui` містить лише latin-ext.
- **Відхилення від макета (за даними й логікою).** Журнал лишається «на навантаження»; конфлікт змін — сповіщення, а не вибір «моя / нова» (OQ-31); без онбордингу, перемикача підгруп на парі, нотаток до студента, undo/redo в конструкторі, вкладок «Місяць / Семестр»; «Самостійна» замінена наявним типом «Контрольна» (OQ-20).
- **Наслідки.** Оболонка: згортаний сайдбар + шапка на десктопі, нижня панель і сторінка «Ще» на телефоні. Перемикач ролі в меню користувача — сегмент-контрол, а не пункти меню.

## ADR-023. Атестації й періоди за курсом; колонки оцінювання без прив'язки до заняття

- **Контекст.** Графік навчання задає різні дати атестацій для 1 курсу і для 2–4 курсів (і сесії немає в першокурсників), а викладач веде практичні та модулі окремими колонками, не пов'язаними з датою заняття.
- **Рішення.**
  - `SemesterPeriod.course` (null — для всіх курсів) і `Attestation.course` (0 — спільні; унікальність `semesterId + kind + course`). Свої дати курсу заміщають спільні того ж виду; спільні лишаються запасним варіантом (`pickAttestation`, `periodsFor`). Дати атестації беруться з періодів курсу групи навантаження; смуга періодів у журналі й події «Сьогодні» теж за курсом.
  - Колонка оцінювання — `Assessment` (`loadId`, назва, шкала, `attestationKind`) з оцінками `Grade.assessmentId` без `lessonId`. Вона має умовну дату — початок періоду своєї атестації для курсу групи, тож потрапляє в модуль своєї атестації й наступні (OQ-23), але не в попередні; без прив'язки — початок семестру. Оцінки колонок враховуються в середньому, прогнозі, зоні ризику, листку атестації.
- **Наслідки.** Журнал показує колонки оцінювання після занять (поки лише перегляд; введення й правка — наступний етап, разом з офлайн-синхронізацією). Імпорт реальних даних: `prisma/import-real.ts`.

## ADR-024. Зведений журнал: один на дисципліну, групу й підгрупу; вид занять — фільтр

- **Контекст.** Викладач хоче бачити всі пари дисципліни в одному журналі, а не перемикатися між «лекції» і «практичні».
- **Рішення.** `GET /loads/:id/gradebook` збирає заняття, відмітки, оцінки й колонки оцінювання з усіх споріднених навантажень (той самий семестр, дисципліна, група, підгрупа; викладач бачить лише свої, деканат — усі). Правила оцінювання беруться з основного навантаження (практична → лабораторна → семінар → контрольна → лекція), тож будь-який `loadId` сімейства дає той самий журнал. У вебі вид занять — фільтр «Усі / Лекції / Практичні…» (стан екрана, без переходу на інший журнал); навігація йде за дисципліною, групою й підгрупою, а список журналів містить по рядку на журнал. Вид оцінки за замовчуванням береться з виду самого заняття.
- **Межі.** Атестації, зона ризику на «Сьогодні» й листок атестації лишаються на навантаження (практичне), тому їхні пропуски рахуються без лекцій, а у зведеному журналі пропуски лекцій входять до загальної відвідуваності.

## ADR-025. Керування колонками оцінювання: окремі API, одна оцінка на студента

- **Рішення.** Колонка (`Assessment`) належить основному навантаженню журналу (практична) і створюється `POST /loads/:id/assessments` (назва, вид «практична / модуль», прив'язка до атестації; максимум — за шкалою; назва унікальна в межах журналу без урахування регістру). `PATCH /assessments/:id` (з версією) перейменовує й змінює атестацію, `DELETE` м'яко видаляє колонку разом з оцінками. Оцінка студента — `PUT /assessments/:id/grades/:enrollmentId` (створення чи зміна, одна на студента, перевірка шкали й складу журналу) і `DELETE` того ж шляху. Права `grade:write` за власником навантаження; закритий семестр — лише читання; зміни в аудиті.
- **Інтерфейс.** Колонки йдуть у сітці після занять; клітинки вибираються стрілками й приймають цифри (як у заняттях), `Delete` прибирає оцінку; заголовок колонки відкриває діалог (назва, вид, атестація, видалення), «+ Колонка» додає нову з підказкою «Практична N» / «Модуль N».
- **Межі.** Редагування колонок онлайн-лише (оптимістичні правки в кеші, без черги синхронізації) і поки лише на комп'ютері; офлайн і телефон — окремі етапи.

## ADR-026. Журнал і екрани на телефоні

- **Рішення.** На телефоні журнал — не сітка, а три розділи: «Студенти» (середній і пропуски, картка студента з оцінками колонок), «Заняття» (список занять із переходом на «На парі»: відмітки й оцінки в тому числі за минулі дати) і «Колонки» (практичні й модулі; тап по колонці відкриває повноекранний список студентів, тап по студенту — клавіатура оцінки без вибору типу, після збереження відкривається наступний студент). Шторка вибору (`BottomSheet`) тепер лежить над діалогами.
- **Проведене заняття можна виправляти.** Підсумок завершеного заняття має кнопку «Змінити відмітки й оцінки» (раніше редагування було лише 10 хвилин після завершення через «Скасувати завершення»). Сервер приймав такі правки й раніше, тож API й черга синхронізації не змінилися; «Готово» повертає підсумок, повторного завершення немає.
- **Вичитка годин** на телефоні — картки з прогресом, прогнозом і нестачею; таблиця лишається на широких екранах.

## ADR-027. Офлайн для колонок оцінювання; порядок списків за замовчуванням

- **Офлайн.** Оцінки колонок проходять через ту саму чергу синхронізації, що й заняття: операції `assessment.grade.set` / `assessment.grade.clear` (без `lessonId`; область операції в outbox — id колонки). Сервер застосовує їх із «останній запис перемагає» по клітинці (колонка + студент) за часом дії на пристрої, ідемпотентно за `opId`, з тими самими перевірками прав, шкали, складу й закритого семестру; REST використовує те саме ядро (`writeAssessmentGrade`). Журнал читається через `loadGradebook`: остання відповідь запам'ятовується в Dexie, без мережі береться копія, а непідтверджені зміни з черги накладаються поверх у будь-якому режимі. Створення, перейменування й видалення колонок лишаються онлайн-діями.
- **Порядок за замовчуванням: курс → предмет → група** (далі підгрупа, вид занять). Курс групи віддається в DTO навантаження; спільний компаратор (`shared/sort.ts`) застосовано в запитах навантажень, груп і дисциплін, у списку журналів, атестацій та «Мої дисципліни» (секції «N курс»), у вичитці годин і навігації журналу.
