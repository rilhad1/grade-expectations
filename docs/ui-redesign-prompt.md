# Промпт для Claude Code: редизайн UI Grade Expectations

> Як користуватися: відкрийте Claude Code в корені репозиторію, покладіть експорт із Claude Design у `design/` (`README.md`, `tokens.json`, `artboards/*.dc.html`, за наявності `screens/*.png`) і вставте текст нижче (від рядка «Ти — …») як перше повідомлення. Робота розбита на фази з зупинками: після кожної фази Claude Code звітує й чекає вашого «далі».

---

Ти — старший фронтенд-інженер і дизайнер інтерфейсів. Завдання: привести UI застосунку **Grade Expectations** (електронний журнал і розклад українського фахового коледжу, PWA) до якісного, цілісного вигляду за макетами з Claude Design, **не зламавши жодної наявної функції**.

## 1. Контекст проєкту (прочитай перед роботою)

- `docs/concept.md` — концепт і оригінальний дизайн-бриф (розділ «СТИЛЬ», «НАВІГАЦІЯ», «ЕКРАНИ»); `docs/PLAN.md`, `docs/DECISIONS.md` (ADR-001…021), `AGENTS.md`.
- Монорепо: `apps/web` — React 19 + Vite + TanStack Router (file-based, `routeTree.gen.ts` генерується) + TanStack Query + Zustand + **MUI 7.3.11** + React Hook Form, журнал на TanStack Table 8 + Virtual. Версії залежностей точні (без `^`), pnpm має перевірку «мінімального віку релізу»: не додавай виняток у `pnpm-workspace.yaml`, а бери старішу версію.
- Реалізовані екрани (все працює, є тести й e2e):
  - викладач: «Сьогодні», «На парі» (`features/lesson`, мобільний пріоритет, **працює офлайн**), «Журнал» (сітка з клавіатурою як у Excel), «Розклад» (тиждень, запит на перенесення), «Мої дисципліни» (тематичний план, правила оцінювання), «Атестація» (модулі, пропозиції, підтвердження, відомість DOCX/PDF), «Вичитка годин» (таблиця + CSV), «Дані й календар» (ICS-посилання, експорт ZIP);
  - деканат (роль MODERATOR): «Конструктор розкладу», «Семестри», «Групи і студенти», «Навантаження», «Запити», «Довідники», «Модерування»;
  - наскрізне: `AppShell` (шапка, бічна панель/шухляда), `SemesterSwitcher`, `WeekBadge`, `UserMenu` з перемикачем ролей, `SyncIndicator` (стан офлайн-синхронізації), вхід.
- Поточна тема: `apps/web/src/app/theme.ts` (primary `#1F3A5F`, фон `#F7F5F0`, шрифт Golos UI/Inter, радіус 6). Усі рядки інтерфейсу — в `apps/web/src/shared/i18n/uk.ts`, англійських слів в UI немає. Спільні компоненти — `apps/web/src/shared/ui/`.
- Чого в продукті ще **немає** (не додавай у навігацію й не малюй «заглушки-обіцянки»): глобальний пошук, «Контрольні», «Звіти», сторінка «Налаштування», темна тема, студентський кабінет.

## 2. Джерело правди для дизайну

- Макети лежать у `design/` (експорт Claude Design; формат описано в розділі 2а). Спершу прочитай `design/README.md` і `design/tokens.json`, потім усі артборди й скриншоти та склади **словник дизайн-токенів**: палітра (світла й темна), акцент, кольори статусів відвідуваності («н», «нп», «з», присутній), підсвітка оцінок (1–3 і 10–12), 6–8 кольорів-міток дисциплін, типографіка, сітка 8/4 px, радіуси (6 для полів, 10 для карток), тіні, межі, розміри зон дотику (мобільний ≥ 48 px). Якщо `tokens.json` чогось не містить (наприклад, темної схеми), виведи значення з макетів і познач їх у плані як «виведено».
- Якщо макет суперечить наявній поведінці чи даним (немає поля, інша логіка) — **поведінка й дані важливіші**: адаптуй дизайн до реальних даних і коротко зафіксуй відхилення у звіті.
- Для екранів, яких у макетах немає («Атестація», «Вичитка годин», «Дані й календар», сповіщення синхронізації, діалоги відомостей), зроби їх у тій самій візуальній мові, використовуючи вже створені компоненти.
- Принципи з концепту: спокійний «академічний» професійний інструмент; один акцент; статуси завжди з літерою, а не лише кольором; табличні цифри (`font-variant-numeric: tabular-nums`) для оцінок, годин, дат, часу; контраст WCAG AA; видимий фокус; повна клавіатурна доступність; дати українською («пн, 5 жовт.»), час 24-годинний; без градієнтів, емодзі, маскотів.

## 2а. Як читати макети в `design/`

1. Спершу прочитай `design/README.md` (формат, карта «артборд → екран», відомі умовності) і `design/tokens.json` (усі кольори, статуси, оцінки, мітки дисциплін, типографіка, розміри). `tokens.json` — джерело правди для `theme.ts`: значення переноси точно, не округлюй.
2. Файли `design/artboards/*.dc.html` — розмітка редактора Claude Design, а не код для копіювання:
   - `{{name}}` — значення з `renderVals()` у `<script type="text/x-dc">` унизу файлу; там же демо-дані й логіка прототипу;
   - `<sc-for>` — цикл, `<sc-if>` — умова;
   - `<dc-import name="X" …>` — вставка компонента з `X.dc.html`, атрибути — пропси (Sidebar, Topbar, MobileNav, LessonMobile, Gradebook);
   - `support.js` — рантайм редактора, ігноруй;
   - стилі inline або в `<helmet><style>` через CSS-змінні (`--accent`, `--line`, `--text-2` …), що відповідають `tokens.json`.

   Бери з них структуру, ієрархію, тексти, розміри, відступи, кольори й стани. **Не переносити дослівно:** inline-стилі, хардкод кольорів, Google Fonts, демо-ПІБ і числа.

3. Еталон спільних компонентів (картка заняття, `StatusChip`, клітинка оцінки, мітка дисципліни, бейджі тижня/ролі/форми контролю, перемикач семестру, порожні стани) — `design/artboards/DesignSystem.dc.html`. Стани системи — `States.dc.html`.
4. Щоб побачити макет, відкрий `.dc.html` у браузері. Рантайму там немає, тож вставки `{{…}}` і компоненти не відмалюються; читай вихідний код як специфікацію. Якщо в `design/screens/` є PNG, порівнюй свої скриншоти з ними.
5. У фазі 0 додай до `docs/ui-redesign-plan.md` таблицю «артборд → маршрут/компонент у `apps/web`» і список місць, де макет розходиться з реальними даними або поведінкою (поведінка й дані важливіші).

## 3. Жорсткі обмеження

1. **Не змінюй бізнес-логіку, API, схеми, `@ge/domain`, `@ge/shared`, offline-шар** (`apps/web/src/offline/*`, `useLesson`, `useGradebook`, мутації й моделі `model.ts`). Змінюй лише презентацію: тему, розмітку, стилі, компоненти. Якщо для макета потрібна нова проп чи дрібна зміна моделі — мінімальна й з тестом.
2. Усі тести мають лишитися зеленими: `pnpm --filter @ge/web test`, `pnpm typecheck`, `pnpm lint`, `pnpm build`, `pnpm e2e`. Селектори e2e (`e2e/specs/*`) спираються на ролі й підписи (`getByRole('button', { name: 'Завершити пару' })`, `data-testid` `row-*`, `cell-*`, `grid`, `status` тощо). Збережи доступні імена й `data-testid`; якщо змінюєш — онови тести в тому ж коміті й поясни чому.
3. Нові рядки — лише через `uk.ts`. Жодного хардкоду тексту в компонентах.
4. Мінімум нових залежностей. Шрифт — Golos UI (self-hosted через `@fontsource/golos-ui` або еквівалент, лише з підтримкою кирилиці, `font-display: swap`); не підключай шрифти з CDN (застосунок має працювати офлайн, а service worker кешує оболонку).
5. Продуктивність: не роздувай головний чанк; журнал-сітка лишається віртуалізованою; «На парі» має бути швидким на середньому Android (без важких анімацій, `prefers-reduced-motion` поважати).
6. Темна тема — обов'язково (перемикач «Світла / Темна / Як у системі» в меню користувача; зберігати вибір у `localStorage` з `try/catch`). Жодних кольорів, прописаних у компонентах: тільки токени теми.
7. Мобільний перший для «На парі» й «Сьогодні»; десктоп щільний для «Журнал», «Розклад», «Конструктор розкладу», «Групи і студенти», «Вичитка годин».

## 4. План робіт (фази з зупинками)

**Фаза 0 — аудит і план (без коду).** Склади таблицю «екран → що змінити → ризики для тестів», перелік спільних компонентів, які треба створити, і словник токенів. Додай таблицю «артборд → маршрут/компонент у `apps/web`» і список розбіжностей макета з даними та поведінкою (розділ 2а, п. 5). Запиши все в `docs/ui-redesign-plan.md`. Зупинись і чекай підтвердження.

**Фаза 1 — фундамент.**

- Токени → `theme.ts` (світла й темна схеми через `colorSchemes` MUI 7 / CSS-змінні), глобальні стилі, типографіка, табличні цифри, фокус, `prefers-reduced-motion`.
- Шрифти, іконки (лише `@mui/icons-material`, імпорт поіменно).
- Бібліотека `shared/ui`: `PageHeader`, `StatusChip` (відвідуваність: н / нп / з), `GradeChip` (тони за шкалою), `DisciplineDot`/мітка дисципліни, `StatCard`, `EmptyState` (з дією), `Skeleton`-варіанти для списків і таблиць, `ConfirmDialog`, `Toolbar`/фільтр-бар, `BottomSheet`, `DataTable`-обгортка для простих таблиць (щільність). Кожен має короткий тест (рендер, доступне ім'я, стани).
- Сторінка «Дизайн-система» (внутрішня, `/design-system`, доступна лише в dev-збірці) зі всіма компонентами в обох темах — для візуального огляду.
- Комміт, звіт, зупинка.

**Фаза 2 — оболонка.** `AppShell`: бічна панель з можливістю згортання до іконок, шапка (перемикач семестру, бейдж тижня, індикатор синхронізації), нижня панель на мобільному (Сьогодні, Розклад, Журнал, Ще), меню користувача (ПІБ, бейдж ролі, перемикач ролі, тема, «Вийти»). Мобільна навігація не повинна зламати e2e `getByRole('navigation', { name: 'Меню' })` — залиш цю landmark. Комміт, звіт, зупинка.

**Фаза 3 — екрани за пріоритетом** (по одному коміту на екран або пару екранів; після кожної пари — скриншоти й зупинка):

1. «На парі» (найважливіший), 2. «Сьогодні», 3. «Журнал» (сітка + картка студента + мобільний перегляд), 4. «Розклад» викладача, 5. «Конструктор розкладу», 6. «Атестація», 7. «Мої дисципліни», 8. «Групи і студенти» / «Навантаження» / «Семестри» / «Довідники» / «Запити» / «Модерування», 9. «Вичитка годин», «Дані й календар», вхід.

**Фаза 4 — стани й шліфування.** Для кожного екрана: завантаження (скелетони), порожній стан із дією, помилка (з «Повторити»), офлайн («Офлайн · N змін на пристрої»), архівний семестр лише для читання, конфлікт/відмова синхронізації. Перевірка доступності (клавіатура, фокус, контраст, `aria-*`), ефективності (розмір чанків) і вигляду в обох темах.

## 5. Як перевіряти свою роботу (обов'язково)

- Запускай `pnpm dev:apps` і відкривай застосунок у браузері (Browser pane): **1440 px** і **390 px**, світла й темна теми. Роби скриншоти й порівнюй з макетами, а не лише з кодом. Демо-дані: `pnpm db:seed`, входи `teacher@demo.local`, `dekanat@demo.local`, `both@demo.local` (пароль — `DEMO_PASSWORD` з `.env`). Демо-«сьогодні» — жовтень 2026; для e2e працює `FAKE_TODAY=2026-10-12`.
- Перед кожним комітом: `pnpm typecheck`, `pnpm --filter @ge/web test`, `pnpm lint`; перед завершенням фази — `pnpm build` і `pnpm e2e`.
- Коміти: Conventional Commits англійською, заголовок ≤ 100 символів, у тілі — 2–4 рядки. Pre-commit (lint-staged з типізованим ESLint) іде кілька хвилин: запускай коміт у фоні й не змінюй відстежувані файли, поки він працює.
- Не роби `git push` і не чіпай `main` напряму: працюй у гілці `feat/ui-redesign`.

## 6. Формат звіту після кожної фази

1. Що зроблено (екрани/компоненти), 2. скриншоти (шляхи) до/після, 3. відхилення від макета й чому, 4. що змінено в тестах і чому, 5. відомі проблеми, 6. питання до мене. Не переходь до наступної фази без моєї відповіді «далі».

## 7. Definition of Done

Усі екрани з розділу 1 мають цілісний вигляд за макетами в обох темах і на двох ширинах; немає хардкоду кольорів і рядків; typecheck/lint/test/build/e2e зелені; Lighthouse (мобільний) для «Сьогодні» і «На парі» — Accessibility ≥ 95; жодна функція (офлайн, синхронізація, відомості, експорт, ICS, конструктор) не втратила працездатності.
