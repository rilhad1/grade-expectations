# Grade Expectations: правила проєкту для Claude

Електронний журнал і розклад фахового коледжу (PWA, мова інтерфейсу українська). Це **живий продакшн із реальними даними** одного викладача, а не демо: помилка в даних шкодить реальним студентам. Концепція: `docs/concept.md`, рішення: `docs/DECISIONS.md` (ADR-001…030), відкриті питання: `docs/OPEN_QUESTIONS.md`, що лишилося: `docs/ui-redesign-backlog.md`, деплой: `docs/DEPLOY.md`, `docs/INFRASTRUCTURE.md`. `AGENTS.md` у корені стосується лише Turborepo (перед зміною `turbo.json` прочитай документацію з встановленого пакета `turbo`).

## Головні правила роботи

1. **Не пошкодити наявні дані.** Розклад, пари, студенти й внесені оцінки налаштовані вручну й працюють. Усе, що пише в базу, спершу перевіряється на локальній копії (`ge_import`) і лише потім іде на Neon.
2. **`git push` не робити без прямої вказівки.** Комітити можна, пушить користувач.
3. **Нічого не вигадувати щодо навчальних даних:** планові години, тематичні плани, по батькові, статуси студентів беруться тільки з даних користувача. Невідоме виносити у звіт, а не вгадувати.
4. **Знищувальні дії** (`--wipe`, `db:reset`, видалення на Neon, `TRUNCATE`) лише з окремим явним дозволом у цьому ж діалозі.
5. **Секрети.** Користувач кидає креди усвідомлено. Зберігати лише в gitignored env-файлах (`.env.neon`, `.env`), не друкувати значення в чаті без потреби, лекцій про безпеку не читати (максимум одне речення нагадати змінити пароль). Ніколи не комітити `.env*` і `data/`.
6. **Автономність:** користувач делегував рішення («роби без моєї вказівки»), але після кожного етапу коротко звітувати: що зроблено, що перевірено, що не зроблено. Спірне й неоднозначне в даних не вирішувати мовчки, а показати користувачу.
7. Безпека (захисні заголовки/CSP, глобальний ліміт запитів, CSV-ін'єкція в експорті, довжина `q`, зміна витеклих паролів) **свідомо відкладена власником**: `docs/ui-redesign-backlog.md` §5. Не «виправляти» без прохання, але й не погіршувати.

8. **Спеки розділів.** Для кожного розділу є спек у `docs/specs/` (індекс і правила користування: `docs/specs/README.md`). Перед будь-якою роботою над розділом **спершу прочитай його спек** і суміжні; зміна не повинна порушувати його «Правила й інваріанти». Після зміни поведінки онови спек (поточний стан, покращення, відкриті питання). Позначки: **[пропозиція]** без згоди користувача не робити, **[питання]** вирішує користувач.

## Архітектурні інваріанти (читай ADR перед зміною)

- **`@ge/domain` без I/O** (ADR-002). Дати в домені й DTO: рядки `YYYY-MM-DD`, не `Date` (проблеми часових поясів; колонки БД `DATE`, UTC-північ). Не робити `new Date('YYYY-MM-DD')` у коді, що залежить від локальної зони (Europe/Kyiv).
- **Ізоляція за коледжем** (ADR-008): `forOrganization(prisma, orgId)` у `apps/api/src/plugins/tenant.ts`; дочірні моделі (Lesson, Grade, Enrollment…) фільтруються через зв'язки в `repo.ts` і `can()`. Кожен новий запит/маршрут мусить бути org-scoped, є тести ізоляції.
- **Схеми оновлення без `.default()`** (ADR-010): у zod 4 `.partial()` лишає default, і PATCH скидав поля. Нову `update*` схему додавати в `packages/shared/src/dto/updates.test.ts`.
- **Офлайн** (ADR-019/020/021): дії на парі та оцінки колонок це операції в outbox (Dexie), до сервера йдуть через `POST /sync/push` (ідемпотентно за `opId`), `GET /sync/pull?since=`. **LWW по клітинці** за `editedAt` пристрою (майбутній час обрізається до серверного «зараз»), REST-запис теж ставить `editedAt`. Єдиний записувач оцінки колонки: `writeAssessmentGrade`. Service Worker **не кешує `/api/*`** (дані офлайн лише через Dexie). Вихід з акаунта/зміна користувача очищує локальну БД. TanStack Query у `networkMode: 'always'`.
- `FAKE_TODAY` лише для e2e (у проді її наявність це помилка конфігурації, ADR-015). `Lesson.manuallyEdited` захищає заняття від регенерації (ADR-004).
- Ідентифікатори: UUID; імпортер використовує детерміновані id (`sha1("grade-expectations-real:"+key)`), не покладатися на них у проді, де частину рядків пересоздано через API (шукати за назвами/зв'язками).
- Soft delete через `deletedAt`: у запитах не забувати фільтр.

## Доменні правила (підтверджені користувачем)

- **Один журнал на дисципліну + групу (+ підгрупа)**; вид занять (лекція/практична…) лише фільтр, не перемикач (ADR-024). Споріднені навантаження (`siblingLoads`: той самий семестр/дисципліна/група/підгрупа); основне: PRACTICE→LAB→SEMINAR→CONTROL→LECTURE. Колонки оцінювання (Практична N, Модуль) живуть **лише на основному навантаженні**; дата оцінки колонки = початок періоду її атестації для курсу групи (ADR-023/025). API: `apps/api/src/modules/journal/gradebook.ts`; веб: `features/gradebook/loadNav.ts`.
- **Атестації й періоди за курсом** (`course`, 0/null = усі курси); вибір атестації: `modules/attestations/pick.ts` (з фолбеком на курс 0). «Модуль 1» = результат 1-ї рубіжної (INTERIM; «є» → «зар.»); колонки до «Модуль» і він сам INTERIM, після нього DIRECTOR_TEST. Навчальні дні рахуються по курсах (ADR-030): сесія 2–3 курсів не блокує 1 курс.
- **Потокові лекції** (ADR-029): спільний `streamId` на навантаженнях груп (КІт-31…34), окреме заняття на групу; конфлікти для потоку толеруються. Конструктор розкладу поки ставить слот потоку для кожної групи окремо.
- **Інформатика 1 і 2 курсів це різні дисципліни** («Інформатика (1 курс)», «Інформатика (2 курс)»): окремі програми й теми.
- Шкала: 1–2 курс 12-бальна, 3–4 курс 100-бальна; форма контролю: залік, крім графіки (екзамен). Відвідуваність: `PRESENT`/`ABSENT`; майбутні заняття в сітці сховані за замовчуванням (ADR-028).
- **Порядок списків за замовчуванням скрізь: курс → предмет → група**, спільний компаратор у `apps/web/src/shared/sort.ts`; курс віддається в DTO навантаження (`group.course`).
- Семестр 2026/27: 1.09–23.12.2026; тиждень 31.08 = «верх» (TOP), 5–9.10 = «низ» (BOTTOM). Пари: 1=08:00–09:20, 2=09:35, 3=11:10, 4=12:50, 5=14:25, 6=16:00, 7=17:35, 8=19:00 (по 80 хв).

### Оновлення даних із Google-таблиці (робочий процес)

1. Користувач кидає xlsx (CSV одного аркуша теж можна, але xlsx повніший).
2. `python3 scripts/export-journal.py "<xlsx>"` → `data/journal.json` (стару копію зберегти як `data/journal.old.json`).
3. Перевірка на локальній копії: `import-real.ts --wipe` зі старим journal у `ge_import`, потім `import-delta.ts` з новим.
4. `prisma/import-delta.ts` **лише додає**: відмітки, оцінки, колонки, результати модуля, по батькові; нічого не перезаписує й не видаляє, не створює заняття, шукає все за назвами в БД. Без `--apply` лише звіт; з `--apply` спершу пише `data/backup-*.json`. Розбіжності з наявним і сумнівні колонки (дати поза розкладом, склеєні заголовки, «Лекція ДД.ММ.РРРР» без `--lectures`) виводить у звіт для рішення користувача.
5. Той самий прогін на Neon: спершу dry-run, порівняти кількості, потім `--apply`; повторний запуск має додавати 0.
6. `import-real.ts` це одноразовий знищувальний імпорт (`--wipe`): не запускати проти Neon без явного дозволу.

## Відомі пастки

- zod 4 `.partial()` зберігає `.default()` (ADR-010).
- Строгий zod-розбір кешованих у Dexie даних ламає старі кеші після зміни схеми: нові поля додавати з м'якими значеннями за замовчуванням (`withDefaults`).
- CSS-сітка журналу: `repeat(0, …)` недійсний і руйнує сітку: сегмент колонок оцінювання додавати лише при кількості > 0. Константи ширин у `GradebookGrid.tsx` (`CELL_W`, `ASSESS_W`, `NAME_W`…) використовуються й у прокрутці до виділеної клітинки: міняти разом.
- Мобільний `BottomSheet` має `zIndex: modal+1`, інакше ховається під повноекранним Dialog.
- Заняття, що вже проведені, редагуються лише через режим «Змінити відмітки й оцінки» (скасування лише 10 хв).
- Дати в таблиці користувача бувають із помилкою в місяці (22.10 замість 22.09): імпорт зсуває/розпізнає їх; не створювати за ними нових занять.
- У проді розклад і частину занять виправляли через API (draft→patch→publish) і окремі скрипти: id рядків там можуть не збігатись із детермінованими id імпортера, тому скрипти, що пишуть у прод, шукають за назвами й зв'язками.

## Проєкт у цілому (детально)

### Користувачі й доступ

- Ролі: `TEACHER` і `MODERATOR` (деканат); у фазі 3 заплановані `COMMISSION_HEAD`, `ADMIN`, `STUDENT`. Один користувач може мати кілька ролей (перемикач ролі на клієнті, ADR-009). Користувачі створюються лише за запрошенням (тимчасовий пароль показується один раз), вхід через Better Auth (cookie-сесія), Google вмикається змінними `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`. Обмеження спроб входу: IP + пошта (ADR-012), вбудований ліміт Better Auth вимкнено.
- Матриця прав: `packages/domain/src/permissions.ts` (`can(membership, action)`), дії: `schedule:read`, `directory:read`, `load:read`, `gradebook:read`, `attestation:read`, `structure:write`, `load:write`, `schedule:write`, `schedule:publish`, `request:resolve`, `lesson:update`, `attendance:write`, `grade:write`, `assessment:write`, `attestation:write`, `program:write`, `gradingRules:write`, `request:create`. Викладач пише лише у власні навантаження; модератор керує структурою й розкладом. На сервері права перевіряються `preHandler`-ами (`plugins/permissions.ts`), у вебі ролі лише ховають UI (не вважати це захистом).

### Модель даних (Prisma, `prisma/schema.prisma`)

- Тенант і доступ: `Organization`, `User`, `Session`, `Account`, `Verification` (Better Auth), `Membership` (ролі користувача в коледжі).
- Довідники: `BellTime` (дзвінки), `Room`, `Discipline`, `DisciplineProgram` + `ProgramTopic` (програма й теми за видом занять, редакції).
- Академічна структура: `AcademicYear`, `Semester` (`firstWeekParity`, `parityAfterBreak`, статус DRAFT/…), `SemesterPeriod` (види періодів, у т. ч. рубіжна атестація, директорська, `EXAM_SESSION`; `course` 0/null = усі курси), `Cohort` (набір: спеціальність + рік вступу) → `Group` (курс, рік) → `Subgroup`/`SubgroupMember`; `Student` + `Enrollment` (статус, `fromDate`/`toDate`).
- Навантаження й розклад: `TeachingLoad` (семестр, дисципліна, група, підгрупа, викладач, вид, години, форма контролю, `gradingRules`, `streamId` для потокових лекцій), `Schedule` (чернетка/опублікована, `revision`) + `ScheduleSlot` (день, пара, парність EVERY/TOP/BOTTOM, аудиторія, `validFrom`), `Lesson` (унікальний ключ `loadId+date+pairNumber`, статуси HELD/PLANNED/CANCELLED/MOVED/…, `manuallyEdited`, тема, домашнє), `RescheduleRequest`.
- Облік: `Attendance` (ключ `lessonId+enrollmentId`, `editedAt` для LWW), `Assessment` (колонка оцінювання: вид LAB/TEST, `maxScore`, `attestationKind`, порядок за `createdAt`), `Grade` (до заняття або до колонки; вид PRACTICE/TEST…, вага, `editedAt`), `Attestation` (на семестр, вид, курс) + `AttestationResult` (підсумок модуля по студенту й навантаженню).
- Службове: `SyncOp` (ідемпотентність push за `opId`), `ChangeLog` (аудит «до/після», ADR-016), `GeneratedDocument` (відомості DOCX/PDF, статус), `CalendarFeed` (секретний токен ICS-підписки).
- Усе, що видаляється, видаляється м'яко (`deletedAt`); `version` на записах для оптимістичного блокування (`VERSION_CONFLICT`, 409).

### Ключові потоки

1. **Розклад → заняття.** Деканат у конструкторі (`routes/_app/admin/schedule-builder.tsx`) створює чернетку слотів → `publishSchedule` рахує різницю «створити / скасувати / без змін» (`generateLessons` у `@ge/domain` із календарем семестру, парністю тижнів, періодами по курсах), блокується конфліктами (`scheduleConflicts`: викладач/аудиторія/група; потоки толеруються) і перевіркою годин, у транзакції зберігає заняття. Проведені, ручні й з відмітками заняття регенерація не чіпає. Теми з програми розкладаються по заняттях (`assignTopicsForLoads`).
2. **Пара.** Викладач відкриває «Сьогодні» → заняття → відмітки й оцінки (екран `features/lesson`); усе йде операціями через outbox, `lesson.finish` ставить HELD і заповнює «присутній» для невідмічених; скасування завершення 10 хв.
3. **Журнал.** `GET /journal/:loadId` віддає сітку студенти × заняття + колонки оцінювання + підсумки (середнє, пропуски, ризик `LOW_GRADE`/`ABSENCES`, пропозиція модуля); введення з клавіатури (`interpretKey` у `features/gradebook/model.ts`), на телефоні `MobileJournal`.
4. **Атестації.** Рубіжна/директорська: відомість по групі, пропозиція (`moduleProposal`, `attestationFinal`), підтвердження викладачем; `requiredModules`, `risk` у домені.
5. **Запити на перенесення/заміну** (`modules/requests`): викладач створює, модератор погоджує (`availability.ts` шукає вільні слоти), заняття переноситься/скасовується.
6. **Документи й календар.** Відомості DOCX (шаблон `apps/api/templates/statement.docx`, docxtemplater; `pnpm --filter @ge/api template:build`) і PDF (Gotenberg, опційно); фонові задачі pg-boss (локально) або inline (прод). ICS-підписка на розклад викладача за секретним токеном (ADR-018, «плаваючий» час).
7. **Синхронізація.** `offline/sync.ts` кожні ~20 с і на події `online` робить push черги, потім pull змін; результат (відхилено/програно LWW) показується користувачу.
8. **Нові семестри.** Майстер (`features/semesters`): новий рік/семестр, періоди по курсах, переведення груп на наступний курс (`promoteGroups`), копіювання навантажень (`cloneSemester`).

## Код-ревю 2026-10-28: повний аналіз

**Метод.** Повне ревю репозиторію (≈43 тис. рядків TS) 10 незалежними рецензентами за ділянками: ядро API й безпека; журнал/атестації/синхронізація; розклад і генерація занять; групи/документи/схема БД; офлайн-шар вебу; екрани викладача; екрани деканату; інфраструктура й імпортери; чистка/ефективність; «висота виправлень» і конвенції. Разом ≈80 кандидатів. 15 найвагоміших перевірено читанням коду й виправлено в коміті `4b3d229`. **Решта кандидатів нижче не верифікована повністю** (рецензенти навели цитату й сценарій): перед виправленням перечитати код, не довіряти сліпо.

**Виправлено (4b3d229):** підроблюваний `X-Forwarded-For` обходив ліміт входу (Worker тепер перезаписує його адресою `cf-connecting-ip`; пряме звернення до Render-origin все ще можна підробити, повний захист: приймати запити лише від Worker через спільний секрет); холодний старт PWA без мережі падав на `getSession()`; `fetchMe` ігнорував кеш при 502/503/504; публікація розкладу падала на м'яко видалених заняттях (унікальний індекс); `promoteGroups` пропускав усі групи когорти, крім першої; блокування шкали не рахувало оцінки колонок і не діяло в `PATCH /loads/:id`; автозаповнення «присутній» у `finishLesson` перебивало офлайн-відмітки (тепер `editedAt` = epoch); дублі оцінки колонки при паралельних записах (advisory lock + перечитування в транзакції); `import-delta.ts` (тайм-аут транзакції, воскресіння видалених оцінок/колонок/результатів); CI без `.env`; необроблена помилка inline-задачі валила процес API; `cloneSemester` губив `streamId`; `GradeSheet` без `key` показував оцінку попереднього студента; жорсткий поріг «низький середній < 4» (тепер із `risk` сервера); індекси `Grade(assessmentId)` і `AttestationResult(loadId)` (міграція `20261028120000_grade_assessment_index`).

**Повторювані патерни помилок (перевіряти в новому коді):**

1. **М'яке видалення проти унікальних індексів** (`Lesson`, `Room`, `Group`, `Subgroup`): видалений рядок займає ключ, нове створення дає 409. Відновлювати рядок або робити частковий унікальний індекс `WHERE "deletedAt" IS NULL`.
2. **Потоки лекцій як спецвипадок** розкидані по сервісах (конфлікти толеруються, а `availability`, ICS, `getLessonDetail`, клон семестру, веб-конструктор опрацьовують потік по-різному). Правильна глибина: одна «сесія потоку» (`streamId+date+pair`), що групується скрізь.
3. **Двокрокове створення на клієнті без відкату** (рік→семестр, когорта→група): збій на другому кроці лишає перший, повтор дає 409.
4. **Дублювання правил у вебі й на сервері** (пороги ризику, агрегація журналу `today.ts` проти `getGradebook`, вибір атестації за курсом у кількох місцях): брати результат із сервера/домену.
5. **N+1 і послідовні запити** на гарячих шляхах (`/today`, `sync/pull`, `sync/push`, `assignTopicsForLoads`) на безкоштовних Render (0.1 CPU) і Neon.

### Незакриті знахідки (беклог ревю, не верифіковано)

**API, дані й транзакції**

- `groups/service.ts`: `createSubgroup` не дедуплікує `enrollmentIds` (409 на композитному ключі); `Group @@unique([academicYearId,name])` і `Subgroup @@unique([groupId,name])` не частково-унікальні.
- - `directory/service.ts`: `Room @@unique([organizationId,name])` блокує повторне використання назви видаленої аудиторії; `deleteRoom`/`deleteDiscipline` без перевірки використання.
- `journal/assessments.ts`: зміна виду колонки (LAB↔TEST) не оновлює `kind` наявних оцінок (ваги розходяться).
- `attestations/service.ts`: `ensureAttestations` лениво копіює дати з `SemesterPeriod` у `Attestation` і більше не оновлює (після редагування періоду відомість і банер «Сьогодні» бачать старі дати); `saveResults` без транзакції й без перевірки `version`.
- `sync/service.ts`: `applyAttendance/applyGradeSet/applyGradeDelete` пишуть аудит окремо від зміни (порушення ADR-016 «в тій самій транзакції»); pull не повідомляє про заняття, передані іншому викладачеві, і про зміни складу групи; push робить ~7 запитів на операцію.
- `moduleProposal.ts`: правило `missedTest='ZERO'` ніколи не спрацьовує (ніхто не виставляє `GradeInput.missed`), опція «Рахувати як 0» у `RulesEditor` нічого не робить.
- `calendar/service.ts`: ICS віддає окрему подію на кожну групу потоку й не фільтрує видалені навантаження; `getFeed` має гонку «знайти або створити» (409 при двох запитах).
- `main.ts`: немає `SIGTERM`-обробника (`app.close()`), inline-документи лишаються `PENDING` після деплою; `env.ts`: `WEB_ORIGIN` із косою рискою ламає перевірку origin, `NODE_ENV` за замовчуванням `development`.
- `schedules/service.ts`: публікація не оновлює аудиторію вже згенерованих занять, якщо змінилась лише `roomId` слота; при скасуванні без створення теми не переприсвоюються; `assignTopicsForLoads` викликається поза транзакцією; `availability.ts` вважає братів потоку зайнятими (запити на перенесення/заміну потоку працюють лише для однієї групи); `MOVED` оригінал блокує повернення заняття на старий час; `deleteLoad` блокується слотами опублікованих історичних ревізій.
- `packages/domain/src/icsCalendar.ts`: `escapeIcsText` не екранує одиночний `\r`; `studentList.ts` не нормалізує апострофи (`'`, `’`, `ʼ`) при пошуку дублів.

**Веб, офлайн**

- `useLogout.ts`: Dexie очищується до `signOut()`; збій мережі лишає користувача залогіненим без офлайн-копії.
- `_app.tsx`/`login.tsx`: користувач із чинною сесією, але без членства, потрапляє в нескінченний цикл `/me` 401 ↔ `/login`; вхід не очищує кеш React Query попереднього користувача (його `['me']` може запустити `bindUser`/sync від чужого імені).
- `offline/sync.ts`: операція, що детерміновано дає 500, блокує весь outbox (карантин лише для 400/422); `lessonSource.ts`: відповідь сервера пишеться в Dexie без транзакції й перевірки версії (стара відповідь перезаписує новіший локальний стан); `network.ts`: будь-який `TypeError` вважається «офлайн» і ховає програмні помилки.
- `offline/sync.ts` опитує кожні 20 с навіть у фонових вкладках (тримає Neon прокинутим); `plugins/session.ts` робить 3–5 запитів на кожен виклик (немає `cookieCache`).

**Веб, екрани**

- Журнал: прокрутка до виділеної клітинки лише по горизонталі (ArrowDown виводить рядок за видиму область); `Tab` завжди «вправо» (і Shift+Tab), фокус не виходить із сітки; `Delete`/`Backspace` не скасовує буфер цифр (через 700 мс оцінка все одно запишеться); версія для PATCH береться з оптимістичної копії (швидкі правки дають `VERSION_CONFLICT`); кнопка «Скасувати завершення» не вимикається після 10 хв; без `loadNav` (інший семестр) зникають перемикач майбутніх занять і фільтр виду; `GradebookGrid` перерендерює весь видимий рядок на кожну стрілку (≈2000 `Box` + підказки), `@tanstack/react-table` використовується лише як список колонок.
- Конструктор розкладу: підрахунок «не розставлено годин» ігнорує курс (`toSemesterInput` відкидає `p.course`, тож для 1 курсу показує нестачу годин, яких API не вимагає); фільтр виду в `UnplacedPanel` лишається після зникнення цього виду, чипи ховаються й нічого не видно.
- Деканат: `schedule.tsx` показує 10 найстаріших запитів замість найновіших (для модератора ще й усі запити коледжу); тимчасовий пароль у `UsersTab` зникає при кліку поза діалогом (повторно його не отримати); майстер нового семестру за замовчуванням позначає для переведення й випускні групи; зміна статусу зарахування (відрахований, переведений, академвідпустка) без підтвердження.

**Інфраструктура й скрипти**

- `db:reset` (`prisma migrate reset`) досі виконується проти будь-якого `DATABASE_URL`; `import-real --wipe` і `seed` тепер відмовляються працювати не на localhost без `ALLOW_REMOTE_DB=1` (`prisma/local-guard.ts`). `moduleProposal`: правило `missedTest='ZERO'` недієве; це доменне рішення, яке чекає на користувача.
- `prisma/import-delta.ts`: пошук семестру/студентів лише за датою/назвою групи без року й статусу; заняття зі статусами CANCELLED/MOVED отримують відмітки; повторювані ПІБ у групі мовчки зливаються.
- Ефективність: `journal/today.ts` робить ≈7 запитів на навантаження послідовно й рахує ризик по кожному виду окремо (розбіжність із журналом); `sync/pull` викликає `getLessonDetail` по кожному заняттю (сотні запитів на знімок); веб опитує `/today` кожні 60 с.
